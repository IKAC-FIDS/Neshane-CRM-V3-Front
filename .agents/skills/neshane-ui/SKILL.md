# Neshane UI

Apply to visible components, layout, styling, interaction, accessibility, or forms. Read `../../../AGENTS.md`, `../../../architecture/governance-baseline.md`, `../../../architecture/standards/component-design.md`, and `../../../architecture/standards/styling.md`. Treat the shared Design System as the owner of semantic tokens, accessible primitives and common interaction patterns while keeping business-specific UI in its feature. Inspect existing tokens/components before adding new ones. Prefer meaningful variants, named metrics, clear states, keyboard/focus support, responsive task priority and first-class RTL/Persian behavior. Keep user-facing language clear and diagnostics secondary. Do not choose a component/styling framework without approval or build speculative generic components.

Deliver focused UI/source changes, relevant executable component/accessibility/RTL tests, and unresolved design decisions. Follow `AGENTS.md` for approved-toolchain dependency resolution, builds/tests, screenshots and isolated local application/container validation. Do not infer a UI-tool choice, production deployment, publishing, push or Security Sign-off.
